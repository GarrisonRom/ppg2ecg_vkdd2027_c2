# v0.52-highfreq4: Higher QRS-Band Loss Weight

## Purpose

This is a controlled ablation of v0.52. The only changed hyperparameter is the
relative weight of the normalized `10-40 Hz` QRS band loss:

```text
v0.52:       low=0.5, mid=1.0, high=2.0
v0.52-hf4:   low=0.5, mid=1.0, high=4.0
```

The three-band FFT decoder, frozen reverse ECG->PPG cycle schedule, dataset
split, seed, batch size, learning rate, and 20-epoch budget are unchanged.
The high-frequency term is still inside `total_weight=0.25`; it is not a
four-fold increase of the complete training objective.

- Dataset: SensSmartTech, subject-wise `22/5/5`
- Sampling: `250 Hz`, window length `2000`
- Seed: `42`
- Epochs: `20` (`10` reverse pretraining + `10` frozen cycle)
- Config: `configs/exp_v052_highfreq4_frozen_cycle.yaml`
- Run: `runs/senssmarttech_v052_highfreq4_frozen_cycle_20ep_seed42/`
- Best checkpoint: `best.pth` (epoch 12, selected by validation `ecg_total`)
- Parameters: `1.411M`

## Results

| Metric | Train | Test |
|---|---:|---:|
| RMSE | 0.7845 | 0.8485 |
| MAE | 0.4511 | 0.5284 |
| PCC | 0.5572 | 0.3175 |
| HR error (bpm) | 9.8188 | 9.3967 |
| R-peak F1 | 0.8164 | 0.8555 |
| QRS width error (ms) | 14.7300 | 14.6439 |

Compared with the original v0.52 high-band weight `2.0` on the test split:

| Metric | v0.52 | high=4.0 | Change |
|---|---:|---:|---:|
| RMSE | 0.8552 | 0.8485 | -0.0067 |
| PCC | 0.3144 | 0.3175 | +0.0031 |
| HR error (bpm) | 8.44 | 9.3967 | +0.9567 |
| R-peak F1 | 0.8920 | 0.8555 | -0.0365 |
| QRS width error (ms) | 8.86 | 14.6439 | +5.7839 |

The higher QRS weight improves global RMSE slightly and gives a small PCC
increase, but it worsens the physiology-facing QRS metrics and HR error. This
does not support selecting `high=4.0` as the new default. It suggests that the
normalized high-band objective is already strong enough at `2.0`, while further
increasing it may over-emphasize band energy without improving temporal peak
localization.

The validation `ecg_total` reaches its best value at epoch 12 (`0.6571`) and
then degrades, so the reported checkpoint remains the validation-selected
`best.pth`, not the final epoch.
